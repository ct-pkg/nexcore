# 决策记录

每条记录：背景、备选、决定、理由、后果、重审条件。编号 D-01…D-19 在文档其他位置被引用。

## D-01：CT 业务核心 + 内嵌 QuickJS

**背景**：业务核心需要跨 macOS/iOS/Android 复用；UI 必须原生；还需要一层可动态编排、可由 AI 大量生成的逻辑。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 纯 JS 核心 | 复用最好、AI 最友好 | 无类型/性能上限、平台能力弱、iOS 热更新合规风险 |
| B. 每平台原生核心 | 性能/平台能力最好 | 三份业务逻辑，复用失败 |
| C. CT 核心 + QuickJS 脚本层 | 核心可复用、类型明确；JS 只做编排；AI 有明确沙箱 | 桥接层复杂；需要 CT/QuickJS 能力验证 |

**决定**：C。Core 用 CT 写纯业务；JS 只做编排/胶水；UI 原生。

**理由**：把“稳定、性能敏感、需要类型”的部分放 CT，把“变化快、可由 AI 生成”的部分放 JS；两层职责不混。

**后果**：必须维护 ABI、线程、协议、Schema 四套契约；桥接层成为关键路径。

**重审**：若 JS 层被证明只做少量胶水，评估去掉 JS、UI 直接调 Core；若 Core 维护成本过高，评估把部分领域逻辑下沉到 JS。

## D-02：UI↔JS 用 JSON 文本，不用二进制

**背景**：跨语言数据需要可调试、可生成、可版本化；团队偏好可读格式。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. JSON 文本 | 可读、QuickJS 原生支持、生成器简单、AI 友好 | 体积/解析开销；数字精度限制 |
| B. CBOR/MessagePack | 紧凑、二进制友好 | 需要额外编解码器；调试差；两套类型系统 |
| C. 自定义二进制 | 最快 | 生成器/调试/兼容成本最高 |

**决定**：A。v1 只支持 JSON；大二进制用 Base64 且有 1 MiB 限额。

**理由**：协议是 UI↔JS 的“低频业务调用”，不是高频数据面；可读性和生成器简单性优先。性能预算在 P4 验证。

**后果**：`int64` 必须在 ±(2^53-1)；大 payload 需要另开通道（Q-04）。

**重审**：若性能验收不达标且瓶颈确认在 JSON，评估“控制面 JSON + 数据面二进制”的双通道，而不是全量替换。

## D-03：单一字符串 ABI + 信封分发

**背景**：ABI 需要稳定、可跨 Swift/Kotlin、可演进。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 每个方法一个 C 函数 | 类型强、调用直接 | ABI 随业务膨胀；每次加方法改 ABI；平台绑定爆炸 |
| B. 单一 `nexcore_send(json)` + 信封分发 | ABI 极小；方法演进只改 Schema；调试统一 | 失去 C 层类型检查；需要协议校验 |
| C. 泛型 `call(method, void* args)` | 比 A 灵活 | 仍需 ABI 类型；跨语言布局风险 |

**决定**：B。ABI 只有 7 个函数；业务方法通过 JSON 信封分发。

**理由**：把“业务演进”与“ABI 稳定”解耦；平台侧只需要一套 transport；与 D-02 一致。

**后果**：类型安全由生成的 C/Swift/Kotlin/JS 绑定承担；必须严格编译生成代码。

**重审**：若某个超高频方法成为性能瓶颈，评估受控的专用 fast path（新 ABI 函数），但默认不做。

## D-04：专用 JS 线程 + 平台 drain 线程

**背景**：QuickJS 单线程；UI 不能被 JS 阻塞；平台唤醒机制差异大。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. JS 在 UI 主线程 | 实现简单；已实测 | JS 长任务卡 UI；平台主线程约束多 |
| B. JS 专用线程 + drain 线程 | UI 不被阻塞；Bridge 平台无关；队列语义清晰 | 需要线程 shim、`JS_UpdateStackTop`、更多竞态测试 |
| C. JS 线程 + 平台 wakeup 回调 | 少一个 drain 线程 | 需要 `DispatchQueue`/`Handler`/`JavaVM` 进入 Bridge，破坏平台无关性 |

**决定**：B。每个 handle 一个 JS 线程；平台 transport 各有一个阻塞在 `nexcore_drain(-1)` 的 drain 线程，负责切到 UI。

**理由**：把平台差异关在 transport；Bridge 只依赖 pthread shim；已验证的“队列 + drain + resolve + pump”机制可以直接沿用。已实测路径是 JS 在主线程，专用线程是差异点，列为 P2 退出条件。

**后果**：多一个线程和一次上下文切换；必须严格测试关闭与线程归属。

**重审**：若移动端线程成本/功耗不可接受，评估“JS 在 UI 线程 + 分片执行”；若桌面端需要多 runtime，另立决策。

## D-05：微任务泵到空，带 turn 预算

**背景**：Promise 链的后续代码必须在下一批消息前完成；但失控脚本不能拖死线程。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 每 turn 泵一轮 | 公平、不会饿死 | 破坏 Promise 链顺序；await 后续可能跨消息 |
| B. 泵到空，无预算 | 顺序最好 | 无限链会卡死 |
| C. 泵到空，带预算 + 中断 | 顺序 + 可终止 | 需要 interrupt handler 与 fatal shutdown 语义 |

**决定**：C，但**区分“让出配额”与“失败预算”**：10,000 jobs 是让出配额（YIELD），达到后立即开 continuation turn 继续泵，job 队列清空前不处理 inbox；真正的失败是连续泵送窗口 > 200 ms 或单脚本 > 50 ms（interrupt handler），置 `abort_requested`，触发 `E_JS_RUNAWAY` 并 fatal shutdown。

关闭路径用**两个独立标志**，不得复用 `abort_requested`：

- `stop_requested`：只让 JS 线程停止取新消息，不作为 interrupt 返回非 0 的条件；
- `close_abort`：关闭 turn 超过硬上限（`shutdown_budget_ms` + 200 ms）时置位，interrupt 返回非 0 抢占当前 job，最终码 `NX_E_CLOSE_TIMEOUT`，不进入 FATAL、不报 `E_JS_RUNAWAY`。

`E_JS_RUNAWAY` 由两类失控产生（单脚本 50 ms、连续泵送 200 ms），不声称单一来源；四种场景（同步死循环、微任务洪水、无限 await、C 侧阻塞）各自走哪个标志、最终码与统计键见 [async-threading.md](async-threading.md) §5.2 的场景表。

**理由**：原“10k 即失败”与验收 ACC-C-03 的 10k 链正好顶在边界，规则自相矛盾。区分配额与失败后，有限长链不会被误杀，失控脚本仍会终止，且不改变“同一链先于下一条消息”的顺序。

**后果**：长链可能跨多个 continuation turn；验收断言改为“全部执行且顺序正确”；预算可配置但需评审。

**重审**：若正常业务出现误杀，按实测数据调整硬窗口，而不是把配额当失败阈值。

## D-06：Schema YAML + Python 生成器

**背景**：需要单一事实源；团队偏好 YAML；生成器本身要可维护、可测试。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 手写四端绑定 | 无生成器 | 漂移必然；AI 无法安全生成 |
| B. Python 3 + PyYAML | 开发快、生态成熟、YAML 解析可靠 | 引入一个开发期依赖 |
| C. CT 自举生成器 | 与项目语言一致 | 需要 YAML 解析/模板/文件 IO，工作量大；CT 限制多 |
| D. 自写 YAML 子集解析器 | 零依赖 | 解析器本身要维护；边界情况多 |

**决定**：B，分两阶段。**P1–P2**：生成器输入是 `src/units.json`（CT 映射清单），只用标准库 `json`，不依赖 PyYAML；因为当前环境没有 PyYAML，且业务 Schema 管线（P3）尚未接入。**P3 起**：业务 Schema 恢复为 YAML（唯一事实源），生成器同时接受 `--spec src/units.json`（必需）与 `--schema ...yaml`（可选）；PyYAML 锁定版本与 hash，作为 P3 的可选开发依赖。`units.json` 不会因为 YAML 回来而删除——命名空间/trait/method 无法从业务 Schema 推导。生成器是开发工具，不进入 App。后续若 CT 工具链成熟，再评估 C。

**理由**：Schema 正确性优先于“零开发依赖”；但在没有 Schema 管线时，先让单元/符号事实可检查，避免生成器靠猜目录。两种输入职责分开，不做双写。

**后果**：CI 需要 Python 环境；生成器版本进入 manifest；`units.json` 与 CT 源文件的一致性由两条检查保证：`--verify-ct build/impl`（缺 trait、缺方法、cname 不存在都失败）与 `check.sh` ⑤b（`.h.ct` 的 `pub` 函数集合必须等于 `methods`）。⑤b 由编码侧落脚本，已随 `check.sh` 全量实跑通过（`SCRIPT_RC=0` + 逐项 PASS）。

**重审**：P3 接入 Schema 时确认 `--spec` 是否仍需要人工维护；若 CT 提供稳定的导出符号清单，可由工具生成 `units.json`，但格式不变。若团队要求零第三方依赖，切换 D 并保留同样的 golden/负例测试。

## D-07：所有事件经 JS 扇出；默认 reliable + 可选 latest

**背景**：两个方向各自维护订阅表会产生分叉、顺序不一致。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 每个方向本地扇出 | 延迟低 | 两套订阅表；native 自发事件可能收不到；顺序难保证 |
| B. 统一经 JS 扇出 | 一套语义；顺序清晰；易测试 | native 事件多一次跳转；JS 关闭时事件不可用 |
| C. 只支持 at-most-once | 简单 | 丢业务事实不可接受 |

**决定**：B + 默认 `reliable`，高频状态事件可标 `latest`。

**理由**：一致性优先；事件不是持久消息，不承诺 at-least-once，但容量内不丢。

**后果**：native 事件在 JS 停止后不可用；需要可靠事实时用请求/响应 + 幂等键。

**重审**：若 native 事件在 JS 关闭后仍必须送达，增加独立的 native 事件总线（另一个决策）。

## D-08：错误码用稳定字符串

**背景**：跨语言错误需要可读、可分支、可演进。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 数字码 | 紧凑、易比较 | 可读性差；文档映射负担 |
| B. 字符串码 | 可读、日志友好、AI 友好 | 体积略大；需要严格表 |
| C. 只传 message | 简单 | 不可程序化分支 |

**决定**：B。`code` 稳定；`message` 不稳定；数值只用于日志。

**理由**：错误处理是一等公民；字符串码在跨语言日志里直接可读。

**后果**：必须维护错误码表；新码只增不改。

**重审**：若协议体积成为问题，增加数字 `number` 字段作为可选优化，不替代 `code`。

## D-09：生成物提交仓库 + CI 漂移检查

**背景**：生成物是运行时输入；构建时生成会让平台构建依赖生成器。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 构建时生成 | 仓库干净 | 平台构建依赖 Python/生成器；不可审计 |
| B. 提交生成物 + CI 检查 | 可审计、平台构建简单 | diff 噪音；需要 `--check` |

**决定**：B。

**理由**：评审者能直接看生成物；平台团队不需要装生成器；漂移可机器检查。

**后果**：Schema 变更必须同提交更新四端；生成物 diff 可能较大。

**重审**：若生成物规模导致仓库膨胀，改为“构建时生成 + 发布 manifest”，但必须保留可审计的发布产物。

## D-10：7 函数 ABI + 不透明句柄 + 冻结 config

**背景**：ABI 要跨 Swift/Kotlin，且不能受 CT 结构体布局变化影响。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 每能力一个函数、多个结构体 | 类型清晰 | ABI 膨胀；结构体布局风险 |
| B. 7 函数 + 单个 config 结构体 | 极小、稳定 | config 字段变更需升版本 |
| C. key-value 配置 | 无结构体 | 可读性差、类型弱 |

**决定**：B。`NexCoreConfig` 无 trait、`struct_size` + `abi_version`、`_Static_assert` 锁定；业务数据走 JSON。

**理由**：结构体只承担启动配置，不承担业务数据；布局风险可控。

**后果**：字段增删/重排要升 ABI 版本；追加可选字段只更新 `NEXCORE_CONFIG_V1_SIZE`（D-18）；平台侧必须用 CT 导出的头。

**重审**：若配置项频繁增加，评估 key-value 或 builder 函数。

## D-11：QuickJS 家族 + v1 不热更新

**背景**：需要小体积、可嵌入、MIT 许可的 JS 引擎；iOS 对下载执行代码有限制。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. QuickJS（Bellard/quickjs-ng） | 小、MIT、易嵌入、C API | 生态/调试工具弱；版本差异 |
| B. JavaScriptCore | Apple 平台原生 | 跨平台差；体积/接口重 |
| C. V8 | 性能/生态 | 体积巨大；移动端嵌入复杂 |

**决定**：A；具体 fork/版本在 P2 锁定（Q-01）。**热更新口径定死为“JS 只随包内置、不从服务端下发”**：JS bundle 在构建期打进 App 包，运行时只从包内加载；Bridge 不提供下载、落盘、替换脚本的 ABI，也不提供指向远端 URL 的配置项。

**理由**：嵌入成本最低；业务是低频编排，不需要 V8 级性能。

**合规约束（不是技术限制）**：这一口径由 Apple App Review 指南 2.5.2 决定——App 不得下载、安装或执行引入或改变 App 功能的代码。因此“不下发”是**合规红线**，不是当前引擎能力不足；即使 QuickJS 完全支持动态加载，v1 也不做。Android 侧同样按此口径统一，避免两端行为分叉。

**后果**：不能用 npm 生态的大部分库；需要自己提供受限 API；任何脚本修复都必须走整包发版。

**重审**：若产品确实需要 JS 下发，必须**单独评审**：先过法务与平台政策，明确是否改变 App 功能、是否需要走审核通道，并给出 ABI v2 的加载/签名/回滚方案；在单独评审通过前，本决定不放开。

## D-12：业务数据一律 JSON，跨 ABI 结构体禁止 trait

**背景**：实测 `use Trait` 会在结构体尾部追加 vptr，且按值嵌套会传染；`ct check` 零诊断。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 业务结构体按值跨语言 | 性能好、类型直接 | trait 布局漂移会让已编译平台二进制错位；Swift 构造 vptr 未初始化会崩 |
| B. 业务数据 JSON，C 结构体只做内部控制 | 布局无关、可演进、可调试 | 一次序列化开销 |
| C. 所有结构体都禁止 trait，业务结构体仍按值 | 性能好 | 依赖生成器/评审纪律；跨版本布局仍需冻结 |

**决定**：B；`NexCoreConfig` 是唯一跨 ABI 结构体，且禁止 trait，布局冻结。

**理由**：实测风险不可接受；JSON 本来就是协议形状；生成器递归检查 trait 作为第二道防线。

**后果**：业务数据有序列化成本；大 payload 受限。

**重审**：若某个数据面被证明必须零拷贝，另立“数据面 ABI”决策，仍然禁止 trait，并用显式布局/静态断言。

## D-13：UI 不直接调用 Core

**背景**：UI 需要业务能力；Core 是纯函数；JS 是编排层。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. UI 直接调 Core | 少一次跳转 | UI 依赖领域模型；绕过 JS 的校验/缓存/降级；两套入口 |
| B. UI 只调 JS，JS 调 Core | 单一入口；JS 可编排；UI 解耦 | 多一次 Promise |
| C. UI 调 JS 或 Core，按方法配置 | 灵活 | 语义分叉；难审查 |

**决定**：B。

**理由**：保持“唯一协议入口”和“Core 纯函数”；性能代价可测量，必要时再评估 fast path（Q-18）。

**后果**：所有 UI 业务调用都经过 JS；JS 关闭时 UI 不能直接使用 Core。

**重审**：若 UI 启动路径在 JS 就绪前必须可用，评估一个受控的“Core 只读 fast path”，但不改变默认入口。

## D-14：回调注册一律生成本地 wrapper

**背景**：实测跨单元 `Fn p = &f;`（`f` 来自 import）CT 退出码 0、零诊断，生成的 C 是 `Fn p = (&f);`，随后 `cc` 报未声明；限定名也不能作为值。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 直接取函数地址 | 代码少 | 静默坏代码；跨单元必踩 |
| B. 在定义单元注册 | 可行 | 生成器要跨单元协调；业务代码位置受限 |
| C. 调用方生成 `static` wrapper，再取地址 | 可控、可检查、跨单元稳定 | 多一层函数 |

**决定**：C。禁止生成任何跨单元 `&qualified` / `= qualified`；需要注册回调时，在调用方生成 `static` wrapper 再取地址。生成 C 中不出现 `::`，跨单元符号一律用 cname 并带 `extern` 声明（GEN-16/GEN-19/SYM-01..SYM-04）。

**理由**：把 CT 的静默错误挡在生成器；wrapper 是显式的、可逐行审阅的。

**后果**：每个回调多一个 wrapper；生成器必须维护符号表（单元、namespace、cname、可见性），不能依赖 CT 诊断。变量不受影响（`&g_var` 会正确生成 `&a_b_mod_g_var`），规则只作用于函数。

**重审**：若 CT 将来修复 `&qualified` 并给出诊断，可简化；在此之前规则不变。

## D-15：Bridge 保留多单元，跨单元调用用映射单元（b′），根转发保留为备选

**背景**：`/tmp/ctmap` 实测：A、B 都是命名空间单元时，只要为每个目标命名空间生成 `<ns>_map.m.ct`（prologue include + 静态 trait + cname recipe），A↔B 双向调用可在同一次构建里编译、链接、运行通过；`a.c` 顶部会带入 `#include "b.h"`，`cc -std=c99 -Wall -Wextra -Werror` 全过。此前“命名空间单元完全无法跨单元调用”的结论作废。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 退回单单元 | 一定能编译 | 无法按固定模式逐条审查 |
| B. 根协调单元转发 | 生成物少；实现集中在根 | 需额外定义注入时机、存储位置、初始化顺序；生成器要同时生成调用与注册两侧 |
| C. 生成的 `<ns>_map.m.ct`（b′） | 点对点依赖；契约是声明式 recipe，规则面小、可机械检查 | 每个命名空间多一个生成文件；需维护 trait/recipe |
| D. `#ct-raw` 手写 extern + cname | **已实测可用** | 把 C 符号与平台细节带入 CT，破坏“无魔法” |

**决定**：C（b′）。消费者写 `import <ns>::<ns>_map`，跨单元调用写 `<ns>::<Trait>.<method>`；映射单元不含实现。B 保留为备选：若 CT 的 import/map 机制变化导致 b′ 不可用，再退回 B，而不是退回单单元。D **已实测可用但主动不采用**（不是未验证）。

**理由**（只保留站得住的维度）：

- **可机械校验性**：b′ 的契约是声明式的 `(ns, trait, method) → cname recipe`，生成器可按符号表断言三处一致、无重复 key、无残留 cname；b 的转发是过程式注册/注入，同样可校验，但需要额外定义注入时机与初始化顺序的断言，规则面更大。这是规则面大小之差，不是“b 做不到”。
- **AI 生成友好度（部分）**：b′ 调用侧形态统一，生成器只改一次；b 要同时生成调用与注册两侧。**回调侧两者相同**，都必须生成 `static` wrapper，“统一形态”不覆盖回调。

**明确不构成差异**（上一版据此判 b 更差，已撤回）：

- 改动处数：b 改“调用点 + 根注册”，b′ 改“调用点 + 目标 recipe”，都是两处。
- 调试栈深度：b 的转发可被内联，“多一层”没有实测证据。
- 耦合方向：中心式 vs 点对点属于拓扑偏好，不构成可判定优劣。

**后果**：

- 每个被调命名空间多一个 `*_map.m.ct` 生成物与漂移检查；生成器需维护“命名空间 → trait → cname recipe”符号表。
- **回调问题不消失**：映射不能取 `&ns::fn`，回调仍需调用方 `static` wrapper（D-14/GEN-16）。
- 原先为根转发写的接口、注入时机、存储位置、初始化顺序、GEN-17/SYM-04、ACC-E-08 正例全部改按 b′ 重写，不保留两套。
- **接口变更三处同步**：目标签名、recipe、调用点必须同时更新；生成器断言三处一致，`cc -Werror=implicit-function-declaration` 做外部兜底。
- **命名与冲突**：recipe key 为 `(ns, trait, method)`；同命名空间多 trait 同名方法由 trait 消歧，落到同一 cname 但签名不同则报错。实现单元禁止 `_map` 后缀；map 不得含函数定义；消费者 import 多个 map 时按 `(ns, trait)` 判断冲突。
- **stale map 与头名**：`--check` 必须检测“多余生成物”；prologue include 用带目录的相对路径，生成器检测头文件 basename 冲突并拒绝。
- 机械检查：`ct build` 退出 0；每个 `.c` 过 `cc -Werror=implicit-function-declaration`；剥注释/字符串后生成 C 无 `::`；recipe 的 callee/目标导出/调用点与符号表三处一致（生成器内部断言 + golden，不冒充外部 grep）；import 两条——**a) 每个实现 `.ct` 必须有 `import <self>;`**（缺了 CT 静默 exit 0 但丢前缀）；**b) 只允许自身 `.h.ct` 与 `*_map.m.ct`，且 `*_map.m.ct` 内部也按同一白名单检查**，不整类跳过。

**重审**：若 CT 修复命名空间单元的 include/符号解析（不再需要 map），删除映射单元；若 map 机制被移除，退回 B。

## D-16：v1 Schema 版本严格相等，`schema_hash` 保持单字段

**背景**：Q-14 要求在 P1 出口前定；三端独立发版是否成立决定 hash 策略。

**备选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 严格相等 | 简单、无兼容负担 | 不能灰度、不能独立更新 JS |
| B. 子集兼容 | 支持增量 | 需生成能力集并在运行时比对 |
| C. 方法级版本协商 | 最灵活 | 协议与生成器复杂度高 |

**决定**：A。`schema_hash` 是单个 64 位十六进制字符串，三端必须完全一致；不一致返回 `NX_E_SCHEMA_MISMATCH`。字段形状冻结在 ABI v1，若将来改 B/C，升 ABI 版本并新增 capability 查询。

**后果**：JS 随包内置（D-11），三端必须同版本发布；灰度为整包灰度。

**重审**：若业务要求 JS 独立发版，选 B，并新增 `schema_capabilities` 字段（ABI v2）。

## D-17：性能基准版本 `bench-v1`

**背景**：原验收只给阈值，没有定义并发度、统计量、计时边界与版本，结果不可比较。

**决定**：

- 延迟固定并发度 1（顺序往返），10k warmup + 100k 采样，报告 p50/p95/p99/max；
- 吞吐单独用 32 并发测（req/s），不与延迟混算；
- 端到端计时包含 JS handler 与 Core handler；另报不含 handler 的分段数据；
- 协议、负载、预算或测量方法任一变化，升 `bench` 版本并记录；
- 设备型号由 Q-16 固化，未固化前阈值标“暂定”。

**后果**：ACC-G-05 可复现、可比较；不允许用“调大数字”替代语义修正。

## D-18：`struct_size` 最小长度语义 + 时钟注入

**背景**：严格相等会放弃前向兼容；没有时钟注入，24h/超时类验收不可复现。

**决定**：

- `struct_size >= NEXCORE_CONFIG_MIN_SIZE` 即接受，尾部未知字段忽略；小于最小值返回 `NX_E_INVALID_ARGUMENT`；`reserved` 必须为 0。
- 两个方向都成立：新调用方 → 旧库（忽略尾部）；旧调用方 → 新库（缺失字段取默认值）。因此新增字段必须有默认值；没有默认值就升 `NEXCORE_ABI_VERSION`，不承诺 backward。
- `NEXCORE_CONFIG_MIN_SIZE` 发布后冻结；新增可选字段只更新 `NEXCORE_CONFIG_CURRENT_SIZE`。
- 新增可选 `now_ms(void *user)` 与 `clock_user`；非空时 Bridge 所有计时只用它（超时、turn 预算、stat）。

**后果**：旧库可被新调用方调用；测试可用假时钟推进 24h。代价是布局断言必须区分“最小已知布局”和“实际参数布局”。

## D-19：关闭顺序只有一处权威

**背景**：评审发现 design/protocol/async 三份文档写了三种顺序，按错误版本实现会导致 `E_SHUTDOWN` 的 `.catch` 不执行。

**决定**：关闭步骤只在 [async-threading.md](async-threading.md) §7.1 定义，顺序为：置 `stop_requested`/STOPPING → `$shutdown` → 拒绝 pending → 泵空（grace 500 ms；超过硬上限 700 ms 由 interrupt 置 `close_abort` 抢占）→ 清 C pending → 释放 runtime → join → `finish_close()` → DEAD。join 只能由非 JS 线程执行；JS 线程内部发起的关闭由后续 `shutdown`/`free` 完成 join；`js_done==false` 走异常路径仍进 DEAD；DEAD 只在 `finish_close()` 单点设置。design §7 与 protocol §12.6 只引用，不重复。四类在途对象（JS pending、outbox 响应、outbox 事件、inbox 未处理请求）按 §7.1 的表格收尾。

**后果**：文档修改必须从 async §7.1 开始；其他文档出现步骤列表即视为评审缺陷。

## D-20：统计键冻结为 `1..18` + `19` 哨兵，5 个新键落在 `10..14`

**背景**：design §6.4 的草案表曾从 `0` 起编号，并把 5 个关闭/预算/超时键放在 `13..17`；这与骨架 `src/NexCore.h.ct` 的实际枚举冲突——`0` 未分配、`10..14` 是预留号、`15..17` 为 `JS_TURNS/JS_JOBS/JS_EXCEPTIONS`、`18` 为 `LAST_ERROR`、`19` 为 `NEXT_FREE`。

**决定**：唯一分配表为 `10 CLOSE_HARD_ABORT / 11 JS_THREAD_ABORTED / 12 JS_RUNAWAY / 13 PUMP_BUDGET / 14 TIMEOUT`；`15..18` 与 `19` 保持不变；`0` 永久未分配。

**理由**：

1. **已实现的键一个都不移动**：`1..9` 与 `15..18` 的数值、语义、宿主统计口径全部不变，属于零改动。
2. **预留段优先占用**：`10..14` 本来就是源码注释里“已分配、未声明、未实现”的预留号；直接落位不产生空洞，`NEXT_FREE` 仍然是 `19`，不需要改哨兵语义。
3. **反向重排代价更大**：若迁就草案的 `0..17`，需要移动全部 **13 个已实现键**（`1..9` → `0..8`，`15..18` → `9..12`）并把 `NEXT_FREE` 从 `19` 改成 `18`，跨 ABI 破坏面更大，且会让已落地的实现与头文件不一致。
4. **`0` 保持未分配**：避免“未初始化/旧实现写 0”被误读成一个合法的观测键。

**后果**：`nexcore_stat` 对 `10..14` 返回 `NX_E_INTERNAL` 且**不写 `*out`**；五个 counter 实现前禁止返回 0、也不得走 `NX_E_INVALID_ARGUMENT`。新增键从 `19` 起顺序追加，`NEXT_FREE` 随之后移。`src/NexCore.h.ct` 的枚举与注释表、design §6.4 的表、实现单元的编号断言 `nexcore_stat_key_frozen` 必须同一次提交更新；验收判据见 acceptance ACC-A-12。**counter 采样不单独立项**：`10..14` 对应的关闭流程、JS 线程、drain pump 在骨架里尚无事件源，现在补采样只能造值，反而破坏“已分配未实现”的语义；随对应子系统落地后实现，计数正确性届时再扩入 ACC-A-12。
