### 2.3 16 条 RC 是否覆盖两阶段关闭（`async-threading.md`）

- 四类在途对象逐类判：
  1. **在途请求**：部分覆盖（C-05/RC 只覆盖 JS pending），**outbox-response 里已生成未 drain 的响应无任何 RC** → 关闭时是被丢弃还是投递，未定义。
  2. **在途事件**：**未覆盖**。`$shutdown` 后 outbox-event 里残留事件的归属未定义（静默丢失？）。
  3. **正在泵的微任务**：部分覆盖（关闭 turn 有预算、RC-16 有中断），但**三份文档给出的顺序互相矛盾**（见下）。
  4. **worker/inbox 队列中已接受未处理的 job**：**未覆盖**。`send` 返回 0 表示已接受，关闭时这些请求既无响应也无终态说明。
- **P0（方案缺陷）**：关闭 turn 的步骤顺序三处不一致——
  - `design.md` §7：拒绝 pending → `$shutdown` → 泵空 → 释放；
  - `protocol.md` §12：`$shutdown` → 拒绝 pending → 泵空；
  - `async-threading.md` §7.1：`$shutdown` → 泵空 → 拒绝 pending → 清空。
  后果：若「泵空」在「拒绝」之前，`E_SHUTDOWN` 的 `.catch` 反应 job 永远不会执行；若在之后，则须再泵一轮。必须定死一条并写明「拒绝后是否再泵一轮」。
- 「resolve 之后 JS 已销毁」：因 JS 侧全部在专用线程串行执行，**不会**出现；但 `nexcore_free` 与 drain 的「检查 drain_active → 销毁」不是原子操作，存在 **TOCTOU UAF**（P0，线程安全）。
- 另：`fatal shutdown`（§5.2 引入）在 ABI/状态机里没有定义——谁触发、句柄是否 DEAD、`send/drain` 返回什么，全部缺失（P0，生命周期）。

### 2.4 19 个错误码与协议自洽（`protocol.md`）

- 超时 / 取消 / 背压三码齐备（`E_TIMEOUT` / `E_CANCELLED` / `E_BACKPRESSURE`），计数复核为 19，**数字正确**。
- 缺陷：
  1. **P1 缺码**：handler 返回值无法序列化（函数/Symbol/循环引用/BigInt）时无对应错误码，现只能落到 `E_INTERNAL`，与「不支持的值显式拒绝」要求冲突。
  2. **P1 语义冲突**：`E_NOT_SUBSCRIBED` 与 §6.1「未知 subId 忽略」互斥。
  3. **P1 行为冲突**：`result` + `error` 同时出现，§13 说「丢弃」，§4 说回 `E_INVALID_REQUEST`；且「丢弃」会让请求方挂到超时。
  4. **P2 未定义**：只有 `id`、既无 method 也无 result/error 的信封。
  5. **P2 命名碰撞**：ABI 错误码与协议错误码有 5 个同名（`E_INTERNAL`/`E_SHUTDOWN`/`E_BACKPRESSURE`/`E_PAYLOAD_TOO_LARGE`/`E_SCHEMA_MISMATCH`），日志无法区分域。
  6. **P2**：`E_CANCELLED` 标 `retryable: true`，与「取消是终态」矛盾。
  7. **P0/P1 协议缺陷**：`$cancel { target: uint32 }` 无方向字段，而两个方向各自用同一 id 空间（§3.1）——同一时刻 UI→JS 的 7 与 JS→UI 的 7 并存时会取消错对象。

### 2.5 生成器规则可机械检查（`codegen.md`）

- 逐条标注「脚本 / 正则 / 人工」。已确认：
  - **只能人读**：`G-10`（沙箱与审查）、`G-14`（模板审查）。
  - **名义有脚本但不可靠**：
    - `G-05`（括号计数/正则算复杂度）：需 AST，正则在字符串/宏上误判；
    - `G-16`（`&ident` 必须本单元定义）：纯正则无法区分局部变量、结构体成员、参数——会对自己生成的 wrapper（`&line`、`&out`）误报；
    - `R-03`（正则收集未定义标识符）：C 的局部变量/宏/typedef 使正则必然误报或失效；应由 `cc -fsyntax-only` 承担（与 G-15 重复）。
  - **与 CT 实测冲突（P0）**：`G-17` 与 `R-01` 要求「生成 CT 源码时，同命名空间内对导入函数用裸名」。实测（`/tmp/ctrepro3`）：命名空间单元对导入单元的函数写裸名 → CT exit 0、原样发射 `f(v)`、**不生成 `#include "mod.h"`**，`cc` 报 `call to undeclared function 'f'`；写全限定 `x::y::mod::f(v)` → CT 直接报 `no function of that name in that namespace`；写 C 名 `x_y_mod_f(v)` → 同样缺声明。即：**命名空间单元目前没有任何可编译的跨单元调用写法**（根单元才会补 `#include`）。
  - 由 `G-17` 第 2 条推出的规则会**复现**审计 §3.7 的 P0，必须整条改写，并给生成器一条实测可用的替代路径（同单元 wrapper 或 `#ct-raw` 声明）。

### 2.6 `NexCoreConfig` 能否冻结

- 已有 `struct_size` / `abi_version` / `reserved`，方向正确；但有 4 个洞：
  1. **P1**：`struct_size` 用「相等」校验 → 任何新增字段都使旧库拒绝新宿主，等于放弃前向兼容。应改为「`>= 已知最小长度`，忽略尾部未知字段」，`abi_version` 只管破坏性变更。
  2. **P1**：`schema_hash` 是**单个定长字符串**。若 Q-14 选「能力集/多版本共存」，该字段形状必须变（数组或指针+长度）→ ABI 破坏。因此 Q-14 必须在 ABI 冻结前定。
  3. **P1**：配置里没有**时钟注入**（也没有分配器/日志回调）。G-05/G-04 的时间类断言只能依赖墙钟，测试不可复现；后续补时钟只能改 ABI。
  4. **P2**：`bootstrap_js` 用 `size_t`，32/64 位布局不同，`_Static_assert` 必须按架构分开写；且 Swift/Kotlin 两侧**没有任何布局自检机制**（A-04 的「CI 失败」无实现路径）。
  5. **P2**：`reserved` 没有使用规则（新库能否读、旧库如何忽略），冻结前应写明。

### 2.8 Q-01..Q-20 临时默认的安全等级

- 分三档：可延后 / 里程碑前 / **ABI 冻结前（P1 出口）**。
- 必须前移到 P1 出口（选错返工成本极高，且会改 ABI 或全部生成物）：
  1. **Q-14** schema 哈希兼容策略 → 决定 `NexCoreConfig.schema_hash` 的形状；
  2. **Q-12** 后台/挂起 → 默认需要 `nexcore_pause`，而 ABI 已定 7 函数；
  3. **Q-03** int64 wire → 决定 schema 类型、校验、全部生成绑定；改一次等于协议大版本；
  4. **Q-13** JS 信任模型 → 决定中断/内存上限/是否签名，影响 F-15 与性能预算；
  5. **Q-06** Swift/Android 集成形态 → P1 就要出 SPM/XCFramework，晚定会重做打包。
- 明确写「保持现状即可」的：Q-07、Q-11、Q-17、Q-18、Q-19（只影响局部）。
- Q-01 QuickJS 版本：维持「P2 编码前」，但补一句「P1 出口前必须锁定候选版本，因为 P2 的 shim 接口按它定」。
